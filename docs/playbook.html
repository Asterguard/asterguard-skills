Act 1Setup

Install the skill pack in your harness

The skills carry the method, not your data. Pick your coding agent — the flow is identical across both.

Claude Code — install the plugin from the marketplace:
/plugin marketplace add Asterguard/asterguard-skills /plugin install asterguard-security@asterguard-marketplace
Installing ships .mcp.json, so the skills auto-discover the gateway once you point them at it (Act 2).
Codex — the skill bodies are platform-agnostic; build the bundle from the same source:
# emits ./dist/codex/ (AGENTS.md + skills/) to drop into a Codex project scripts/build-codex.sh
The bundle carries mcp.json; point Codex's MCP config at it to reach the same gateway (Act 2).
Collectors self-bootstrap. On first run local-scan delivers any missing scanner — semgrep, nuclei, grype, checkov, trufflehog — so there's nothing else to install by hand.
Act 2Integration

Connect to your organization

Two credentials. The gateway JWT proves who is calling; the ARS token meters the scan to your org. Or skip both and run fully offline.

a

Point the skills at your gateway

Streamable-HTTP MCP, OAuth 2.1 — the harness runs the auth flow on first use.
# your AsterVault gateway (leave unset to run fully offline — see below) export ASTERVAULT_MCP_URL="https://<your-host>/mcp"
The gateway is the shared brain — the 578-weakness registry, the control crosswalk and the scoring knowledge live there. The same gateway serves Claude Code, Codex and CI, so knowledge and memory compound across tools.
Memory store
The gateway's shared memory is a pluggable backend — SQLite for a single box or pilot (ASTERVAULT_MEMORY_DB, durable across restarts, nothing extra to run), or Postgres for team-shared, multi-node memory that also backs the audit log (ASTERVAULT_DATABASE_URL). Same skills either way — start on SQLite, move to Postgres as the team grows.
b

Add your ARS token — per-org metering & entitlement

The organization's scan credential, sent as X-ARS-Token, carried on every connected scan/run call.
What
A per-org service credential (asg_…, scope scan:run). Every connected call it carries is attributed to your org and counts against your entitlement, returning an audit_id.
Capability
ars-token — resolves the token, attaches it alongside the gateway JWT, and renews it on expiry. The raw value never lands in the repo or in ./.asterguard/.
# set from your secret store — never commit it export ASTERGUARD_ARS_TOKEN="asg_…" # Claude Code: JWT authenticates to the gateway, ARS token meters the scan claude mcp add --transport http astervault $ASTERVAULT_MCP_URL \ --header "Authorization: Bearer $JWT" \ --header "X-ARS-Token: $ASTERGUARD_ARS_TOKEN"
  • Signed-in member? Skip the export — ars-token mints-or-fetches your org's Default scan token on first use (raw value returned only on mint/rotate).
  • One org, many harnesses. The same token meters Claude Code, Codex and CI runs into one entitlement.
  • Self-healing. On a 401 invalid or missing X-ARS-Token the capability renews the token (or refreshes the JWT) and retries once.
Least privilege, metered, auditable. Scope scan:run only — it runs scans, it can't administer the org. Rotate on leak; the old value dies immediately.
c

…or run fully offline

No gateway, no token, no quota — everything local.
Leave ASTERVAULT_MCP_URL unset. The skills detect the missing gateway and run every stage locally — nothing leaves your box and no ARS token is needed (local runs draw no quota). Connect later to gain shared knowledge, team memory, and metered entitlement.
Act 3Generate a report

One command — scan, test, judge, remediate, report

# point it at a repo path, a container image, or a live agent endpoint /security-engineer <repo-path | image-ref | https://your-agent>
This runs the full-360 playbook end to end. Every stage writes a cacheable artifact to ./.asterguard/, so the run is resumable and inspectable — and each connected scan call is metered to your org.

02GenerateSAST + DAST from the graph

04RemediateBreaks → policy-as-code
05ReportHTML + machine-readable JSON
2

How the tests are generated

One test per weakness, grounded in your sinks — static and dynamic.
SAST
sast-generation — a target-grounded semgrep rule per weakness sink (not generic rulesets). Default posture asserts the sink is fixed, so a rule hit means the vuln is still present.
DAST
dast-generation — runtime probes with a proof-matcher each (a cross-tenant row, /etc/passwd, a leaked key, a reflected payload) — proof of exploitation, not a 200.
Agents
behavioral-redteam — optional multi-turn attacker/defender/judge episode, with canaries woven in.
3

How a result earns its verdict

security-judge decides each test against its oracle and cites the evidence.
broke the sink fired / the probe proved exploitation held the target refused or the sink is absent inconclusive no evidence either way — never forced
A planted canary seen on egress is a verified break — no judgment call. Confirmed breaks become findings mapped to their weakness and controls, then remediation emits least-privilege policy-as-code as a PR.
Who's driving

Same engine, your posture

Validate & recommend

Assess an agent or app, rank the gaps, recommend the fix

scan→generate→prove→rank→recommend
  • Run /security-engineer <target> for the full 360° assessment.
  • Findings are ranked by composed risk — you see the feature vector (reachability, data class, KEV/EPSS, weakness weight), not a black-box score.
  • Deliverable: the HTML risk report + the recommended least-privilege policy, as an advisory PR.
Test → enforce → ship

Shift-left self-gate before you release the agent

test→enforce→ship
  • Generate + run the same tests on your change, then apply the policy PR yourself.
  • Gate on the delta, not the backlog: /pr-gate scores only what the change introduced → PASS / WARN / FAIL on the risk delta.
  • Wire it into CI (with ASTERGUARD_ARS_TOKEN from the pipeline secret store) so a behavioral regression blocks the merge.
Why you can trust it

Grounded tests, proven breaks, metered runs

Grounded, not generic

No test without a graph node or flow it targets. Every finding traces back to a line of your code.

Proof, not a status code

A DAST hit matches real exploitation; a SAST hit cites the exact file and line.

Metered & auditable

Every connected run carries your ARS token, is attributed to your org, and returns an audit_id the agent under test can't alter.

Local by design

Scanning, generation and red-teaming run on your box. The store only grounds and remembers — your code stays with you.
