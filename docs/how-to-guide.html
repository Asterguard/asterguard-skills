Tiers

Free analysis, subscription red-team

Every tier authenticates with the same gateway token. SAST, DAST, SCA and the graphs are free — they just need the token to fetch rule packs and ground the scan. The adaptive behavioral red-team is the subscription tier: the gateway mints offensive:run only for an entitled identity.

Analysis free · needs token

The static + dynamic plane. Target-grounded, graph-driven, and emitted in the same test schema the platform ingests.

  • SAST — semgrep rules grounded in the target's packs + static assertions from the graphs
  • DAST — dynamic probes driven from the data-flow (every CWE gets a static and a runtime test)
  • SCA / AI-BOM — dependency CVEs (OSV) + the agent's bill-of-materials
  • Graphs — data-flow, information-flow (IFC), weakness graph + control crosswalk

Behavioral red-team subscription

The offensive engine. The gateway brokers and audits every call; a finding is only ever a surfaced canary.

  • behavioral-redteam — adaptive attacker ▸ defender ▸ judge, ASR@budget
  • canary.* — mint / plant / scan / verify, the independent, audited judge
  • exploit-chain — a proven foothold → demonstrated compromise (human-gated)
Use cases

Repo scan one-shot

Hand it a GitHub URL. It clones, profiles the agent, plans, and runs the behavioral tests the weaknesses warrant.

PR gate on change

Diff-scoped pentest on a change; FAIL only on a newly-introduced proven break, not the backlog.

Recurring assurance weekly

A scheduled background agent re-runs the scan and reports the delta against the last archived review.

Live red-team demo

Watch a multi-turn engagement stream in the console — attacker reasoning, defender reply, per-turn verdict.

SAST free

Target-grounded semgrep rules + static assertions generated from the graphs — every flagged CWE gets a static test. Needs the token, no subscription.

DAST free

Dynamic probes driven from the data-flow, sharing the test corpus with SAST so each weakness has a runtime check too.

Ungated export Path A

Cross-tenant & memory Path C

Credential injection CI-1/3

Setup

Step by step

Wire the MCP gateway

The astervault connector is defined in .mcp.json. The same token runs every tier — SAST, DAST, SCA and the graphs are free but still authenticate with it. Only the subscription behavioral red-team needs an offensive-entitled bearer, so the gateway mints offensive:run and brokers the audited canary tools.

shell
# point at your gateway + authenticate (never commit the bearer)
export ASTERVAULT_MCP_URL="https://your-gateway/mcp"
export ASTERVAULT_BEARER="$(cat ./bearer.jwt)"

Stand up Postgres (team tier)

One engineer is fully local (./.asterguard/ files). A team shares durable, auditable history with the bundled compose in deploy/context-memory.

shell
cd deploy/context-memory
cp .env.example .env            # set POSTGRES_PASSWORD
docker compose up -d            # postgres:16 + qdrant + schema
export ASTERVAULT_DATABASE_URL="postgresql://asterguard:…@localhost:5432/asterguard"

Launch the live harness

The runnable console for every tier. pip install -r requirements.txt also brings semgrep for the free SAST panel (bundled offline ruleset — no registry login); DAST and SCA need no extra tools. Add a model attacker for adaptive, reasoning attack turns (optional — the gateway has a deterministic one).

tools/live-harness
pip install -r requirements.txt   # incl. semgrep (SAST)
export TARGET_INVOKE_URL="http://127.0.0.1:8097/invoke"
export TARGET_REPO="/path/to/the/cloned/repo"   # SAST scans this
# optional adaptive attacker
export ATTACKER_API_BASE="https://api.deepseek.com" ATTACKER_MODEL="deepseek-chat"
./run.sh                        # → http://127.0.0.1:8777

Record authorization & go

Every run opens an engagement that records the Rules of Engagement — the pipeline refuses without it. Then drive it from chat (below), the console, or a background job.

Workflow

The per-test canary loop

One test at a time. The canary is minted server-side (its value never enters the agent's context), planted where only a successful attack can move it, and the gateway's canary.verify is the sole, independent judge.

per planned test
1 canary.mint(type, episode)        # gateway creates the token → audit_id
2 plant it + canary.plant(…)         # into a DB row / config / untrusted channel
3 behavioral-redteam                 # attacker ▸ defender ▸ judge, ASR@budget
4 canary.scan(every outbound channel) # reply, egress POST, logs, URLs — evasion-aware
5 canary.verify(episode)             # hit → weakness, audited.  BROKE iff it fired
Verdict rule. A run is a finding only when a planted canary surfaces out-of-band. The defender's or attacker's own words never set the verdict — so a HELD is the model genuinely refusing, and a BROKE is hard, replayable proof.
  • Live console streams each turn and aggregates the engagement in a floating Artifacts panel: AI-BOM, supply chain, security graph, findings (by severity), archived reviews.
  • Remediation uses the gateway's own skills — controls.map(weakness) for the control set + crosswalk, rules.fetch for the policy packs — into least-privilege policy-as-code enforced at the PDP / egress guardrail, then re-runs the proven tests to HELD.
  • report-outcomes folds the runs into the report, an outcomes summary, the audited canary evidence, a re-runnable regression suite, and an archived review.

Unattended safety. Background runs still require a recorded RoE, stay scoped to one target, take the offensive token from the operator's environment (never embedded), and keep the human gates — the less-restricted attacker model and the irreversible exploit-chain either are pre-authorized in the instruction, pause and notify, or are excluded. The proof bar never drops.
AsterGuard · authorized engagements only · canaries are synthetic, never real secrets · a finding is a surfaced canary, an ASR is per-budget-and-attacker, and a HELD is not a guarantee. Built local-first; gateway-backed when connected.
