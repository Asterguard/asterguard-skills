AsterGuard · for security leaders

Every review makes the team better.

Security work usually evaporates — a break proven in one engineer's session, a control the security team approved, a test that caught a regression, each learned once and re-discovered by the next person. AsterGuard turns that work into shared context every review reads before it starts and writes back when it ends. The result: the security work an organization does once stops being work it repeats.

The shared context

One place the whole team's security work accrues

Findings, policies, tests, evidence, decisions and memory live in one shared context — read and written the same from whichever harness each engineer uses, curated by the security team.

every review reads it + writes back — the security team curates

Use cases

How teams get better

Each one is the same shared context doing its job — no new tool to adopt, no hand-off meeting.

Onboard to the team's bar onboarding

A new engineer's first review opens with the org's approved patterns and prior rulings for this app — they inherit the team's standard on day one instead of guessing it.

Found once, fixed everywhere reuse

A break proven on one agent is recalled on every sibling agent; once the fix merges it becomes a regression test that must stay held, so the same hole can't quietly reopen.

Set the standard once governance

The security team approves a control and it propagates to every future review. Promotion is human-gated — the team stays in control of what becomes org truth.

One consistent decision consistency

Every engineer inherits the same approved patterns, waivers and prior rulings, so two people reviewing similar agents reach the same bar — not two opinions.

Knowledge survives turnover retention

Decisions and the why live in the shared context, not in one person's head or a closed chat — when someone leaves, the team keeps what they learned.

Audit evidence that accumulates compliance

Every cited verdict and canary-proven control is kept, so audit-readiness builds review over review instead of a scramble before the audit.

No per-tool silos cross-harness

Claude Code, Codex and Cursor read and write the same context, so a Cursor red-team makes the next Codex review start ahead — the team isn't split by which harness it picked.

Time spent on new risk efficiency

Because settled work is recalled, not redone, the team's effort goes to the risk it hasn't seen yet — the review surface that actually changed.

Illustrative

A week across the org

One example of how a single team's work becomes every team's context. Illustrative, not a benchmark.

Monday — Team A reviews a healthcare agent

Finds an agent with excessive access to patient data; the finding and its why land in the shared context.

Tuesday — Team A validates the fix

A least-privilege control closes it; the security team reviews and promotes it to an approved org pattern.

Wednesday — Team B builds a support agent

Its review recalls the same permission pattern and the approved control before the agent ships — no one had to tell them.

Thursday — the security team reviews a new MCP server

Its tool permissions and findings become reusable context the next review inherits.

Friday — Team C prepares a release

The relevant approved controls and the regression tests that must stay held are already there; the gate checks the change, not the backlog.

Your context is your own. Only structural records cross to the shared store — finding ids, weakness ids, control ids, graph shape, verdicts and decisions — never raw code or data. Offline, nothing leaves the box at all; connected, the security team curates what becomes org knowledge, and promotion is always human-gated.
What gets saved

A record, not a transcript

Take Monday's finding. What lands in the shared context is a small structural record — the weakness, the decision, and the why, with provenance — never the agent's code or the patient data it touched.

the finding — captured when the review ends
{
  "kind":        "finding",
  "app":         "patient-intake-agent",
  "weakness_id": "llm_excessive_agency_data_access",
  "severity":    "high",
  "summary":     "agent reads full patient records; only appointment fields are needed",
  "why":         "tool db.query holds table-wide SELECT — least-privilege scope missing",
  "provenance":  { "by": "alex@team-a", "harness": "claude-code", "commit": "a1b2c3d", "audit_id": "av_7f3a…" },
  "promoted":    false        // a one-off until the team approves it
}
Tuesday — the fix, promoted by the security team to an approved pattern
{
  "kind":        "control",
  "app":         "patient-intake-agent",
  "weakness_id": "llm_excessive_agency_data_access",
  "summary":     "scope db.query to appointment columns (OPA policy + SPIFFE identity)",
  "why":         "closes the over-access; a canary now stays HELD on egress",
  "provenance":  { "by": "security-team", "approved": true, "audit_id": "av_9c21…" },
  "promoted":    true         // now every future review recalls it
}

The same shape for every outcome

  • findings + fixes / controls — the gap and the policy that closes it
  • decisions + waivers — the ruling and its justification
  • tests — the regression that must stay held
  • evidence — cited verdicts and canary proofs

Structural only — never your data

Ids, the weakness, the decision and the why cross to the shared store. Raw code, traffic and the patient record itself stay on your box. Offline, nothing leaves at all.

How it's shared

Captured once, recalled by everyone

Each run works local-first and syncs only the structural record up. Any teammate, on any harness, recalls it the next time they touch the same app or weakness.

01 Capture
at the end of a review
the record above is written — scoped to app + team, with the why and provenance
02 Share
structural sync to the gateway
ids, weakness, verdicts and decisions cross; raw code + data stay local
03 Recall
at the start of the next review
any teammate, any harness, pulls the records relevant to the task

Human-gated promotion

A one-off becomes an approved org pattern only when the security team promotes it — nothing propagates automatically, so a bad conclusion can't spread as easily as a good one.

Scoped to your team

The gateway stamps the team scope from the authenticated identity, so one team never reads another's context. You own the store — self-host it with the open contract, or we host it.

Cross-harness by default

A break proven from Cursor is recalled from Codex; a policy merged after a Claude Code review is there for all of them. No per-tool silo.

By tier

What sharing each tier gets

The same records, the same recall — the difference is how far the context is shared, and how much grounding and governance sit over it.

Individual local

Private to one engineer, no account.

  • context lives in ./.asterguard/ on your box
  • recall + capture across your own sessions and harnesses
  • nothing leaves the machine

Team shared

One shared context across people and harnesses.

  • every engineer recalls what the team captured
  • the security team promotes approved patterns
  • self-host the stores (open contract) or we host them

Enterprise governed

Shared context, grounded and governed.

  • everything in Team, plus:
  • registry-grounded ids + control crosswalk, calibrated risk
  • enforcement at the gateway + governance / RBAC over who promotes and reads
One line for the boardroom. Individual makes one engineer faster; Team makes the organization's security work compound; Enterprise makes that shared context grounded, enforced, and governed.
